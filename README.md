# Agent Government · 三省六部 AI 治理体系

> 用中国古代官制（三省六部 + 内阁 + 御史台）治理你的 AI Agent——一套经过真实多工具环境落地的角色契约、职能路由与记忆制度。

## 为什么需要"官制"

如果你在用多个 AI 编码工具（Claude Code / Codex / ZCode / DSH……）长期维护一批项目，大概率撞过这五堵墙：

1. **上下文易失**——每次会话新开，AI 不记得上周的判断和教训
2. **自我复核不可信**——同一个模型既起草又审核，等于自己给自己签字
3. **多工具无协调**——三个工具各改各的，互相覆盖、记忆分叉
4. **需求无路由**——写作、开发、查资料全挤一条流水线，或者根本没有流水线
5. **AI 越权**——顺手改全局配置、自动批准自己的方案、替你做了本该你拍板的决定

本仓库的答案不是又一个 Agent 框架，而是一层**制度**：把"谁起草、谁审核、谁执行、谁监察、谁拍板"拆开，用角色契约（文件）+ 官员记忆（档案）+ 职能路由（分部）固定下来。**官制是加法不是框架**——不替换你现有的任何工具，只给它们发官印。

## 核心理念

| 理念 | 一句话 | 对应的制度设计 |
|---|---|---|
| **官如流水，吏如磐石** | 有判断权的智能体只在任务期间上任；无判断权的程序常驻运行 | 调度脚本（吏）24 小时在岗零裁量；官员按需实体化，任满销毁、档案留档 |
| **拟票者不批红** | AI 可以拟方案（票拟），选择权永远在人（批红） | 内阁三揆只出纸不动手；涉全局规则/不可逆/对外发布/付费的谕旨必须人批 |
| **三省是工序，六部是职能** | 决策流（草诏→封驳→执行）与职能分区（吏户礼兵刑工）正交 | 需求先路由到部，再走工序流水线 |
| **制度记忆跨区，案卷不出区** | 官员的手艺跟着官走，项目的秘密留在本区 | 官员宦历档案放全局；A 区项目事实结构性无法带入 B 区 |
| **审核者不能是起草者** | 同一执行者的复核必须如实标注，不冒充独立 | same_tool 原则：三票阁议互不可见，票源如实标注 |
| **巡按不驻防** | 监察定期流动巡查，不常驻、不勾结、不成为瓶颈 | 一个御史按六部清单巡检，发布后抽验 1 项 + 周五巡按 + 异常弹劾 |
| **祖制条例** | 立法权专属用户；内外风险分治——外患只能防御，内忧必须根治 | 风险条例四权分置（立/存/用/查各归一署）；豁免留痕；违规必报禁静默修复 |

## 官制全图

```
皇帝（你）── 批红（大事必朱批，无代理、无默认、不设自动批准）
  │
内阁（跨区·三揆·只票拟不执行）
  │  输出"谕旨"：处理决定 + 路由 + 是否请批红
  │  密揭/阁议/会签三级 · 拟票互不可见 · 分歧原样保留
  │      ↑封驳谕旨：门下省（侍中）   ↑封驳票拟：御史台
  ↓谕旨（小事直达执行，大事待批红后下达）
三省六部（不入阁·行政体系）
  中书省：接谕旨草"题本"（任务契约/设计/验收标准）
  门下省：封驳谕旨 + 属官复核交付物
  尚书省：仆射＝当前工作区会话模型（尚书令＝调度脚本，虚悬）
    └─ 六部（各工作区职能分区）：吏/户/礼/兵/刑/工
御史台（跨区·独立）：巡按六部清单 · 发布后抽验 · 专项弹劾
  核档（官员宦历 vs 实际证据）· 销案复核 · 封驳票拟
```

**官职与工具的映射**（重点：程序永不掌握判断权）：

| 官名 | 实际对应 | 关键约束 |
|---|---|---|
| 皇帝 | 用户本人 | 批红权专属，无代理 |
| 内阁三揆 | 三个独立拟票智能体（或一个智能体三视角） | 三不准：不吞分歧/不代批红/不票拟时执行 |
| 中书令 | 需求分析角色 | 草"题本"（怎么做），不决定路由（做不做） |
| 侍中 | 独立复核角色 | 封驳谕旨 + 复核交付物，永不票拟 |
| 尚书令 | 任务调度脚本 | **虚悬**——名器给程序，判断权永远在智能体和用户 |
| 尚书仆射 | 当前会话模型 | 实际调度执行 |
| 六部尚书 | 各职能分区牵头契约 | 会签权（从本部视角审票），部职不入阁 |
| 御史 | 独立审计智能体 | 只查不改；不得是同一任务的执行者 |

## 快速开始

把本仓库接入你自己的多 AI 工具环境，三步：

**第一步：定职能路由（六部）**

复制 [`docs/职能分区.md`](docs/职能分区.md)，按你的工作类型改六部表。示例映射：吏=记忆规则、户=知识检索、礼=写作、兵=开发、刑=测试审计、工=基建运维。不必凑满六部——从两三部起步。

**第二步：立契约与档案**

- 把 [`templates/`](templates/) 里的契约放进你的 agents/ 角色目录（多数 AI 工具都支持"角色文件/子智能体定义"）
- 建 `records/` 目录，用 [`templates/records-template.md`](templates/records-template.md) 初始化每位官员的宦历档案
- 在你的工具入口文件（AGENTS.md / CLAUDE.md / system prompt）里加一句：任务开工先读官制总纲定路由

**第三步：接上你已有的机制**

官制不新建执行机制，映射到你现有的工具：

| 官制职能 | 你可以用 |
|---|---|
| 尚书省调度 | 任何任务流水线脚本、TODO 工具、todo 机制 |
| 占用/锁 | 任何文件锁（防止两个会话同时写同一文件） |
| 巡按触发 | 定时任务（cron / 计划任务）跑审计脚本 |
| 票拟批红 | 你所用工具的计划审批模式 / 提问确认机制 |
| 官员记忆 | 普通文件 + 按需检索（详见 [`docs/官员记忆规范.md`](docs/官员记忆规范.md)） |

## 与同类项目对比

多智能体"组织化"路线已有多个实现，本项目定位不同——**它们是跑在特定平台上的执行框架，本项目是工具无关的治理制度层**（纯契约文件，任何工具均可接入）：

| | [Edict](https://github.com/cft0808/edict) (17k★) | [Emperor](https://github.com/solonlab/Emperor) | [MetaGPT](https://github.com/foundationagents/metagpt) / [ChatDev](https://github.com/OpenBMB/ChatDev) / [CrewAI](https://github.com/crewAIInc/crewAI) | 本项目 |
|---|---|---|---|---|
| 隐喻 | 唐朝朝廷 | 三省六部 | 现代公司（软件公司/团队） | 三省六部+内阁+御史台+翰林 |
| 形态 | OpenClaw 平台 | OpenCode 插件 | 代码框架 | **纯制度契约（md 文件）** |
| 决策/执行分离 | 三省分权 | 三省分权 | 角色 SOP 流水线 | 内阁三揆票拟（谕旨）与中书省（题本）分文书 |
| 独立监察 | 系统审计日志 | ✗ | ✗ | **御史台**（巡按/核档/风闻奏事/封驳票拟） |
| 跨会话官员记忆 | 国史馆在 Roadmap | ✗ | ✗ | **翰林三级记忆**（起居注→实录→国史，修史权分离） |
| 人工审批 | 御批在 Roadmap | 敏感词触发 | ✗ | **批红权制度**（必批四项，无代理无默认无自动批准） |
| 诚实性标注 | ✗ | ✗ | ✗ | **same_tool 原则**（同模型多票不冒充独立意见） |
| 官员生命周期 | 常驻 Agent | 常驻 Agent | 常驻角色 | **官如流水**（按需实体化，档案重建式记忆） |
| 防制度退化 | ✗ | ✗ | ✗ | **防退化条款**（不设东西厂、三省衰亡教训为防火墙） |

一句话：Edict 们造的是朝廷，本项目写的是官制。两者不互斥——执行框架可以按本契约接入这套治理层。

## 工程实现提示

- **批红的轻量实现**：可用敏感词/操作类型检测（删除、生产环境、密钥、对外发布、付费等）自动把谕旨升级为必批——Emperor 的 mixed 模式即此思路。注意：关键词检测只是护栏，判断权仍在用户，不可把"未命中关键词"当作免批依据。
- **分拣在先**：接入时先做消息分诊（闲聊直答、旨意入流），防止把每次对话都升格成全套流程。

## FAQ

**Q: 官员为什么不做成常驻智能体？**
常驻=上下文越积越脏（跨项目串味）、锚定固化（第一单的偏见污染之后所有任务）、单点故障、不可审计。"官如流水"让每次唤醒都被契约重新约束、新开干净上下文、天然并行。需要 24 小时在岗的职责交给"吏"（无判断权的程序）。详见总纲。

**Q: 我只有一个 AI 工具，能用吗？**
能。三省的"工序"在单工具里就是同一模型的三个阶段（先分析、再互相盲审、再执行）；阁议三票用子智能体（如果支持）或同一模型的多次独立生成实现，票面如实标注即可。

**Q: 为什么用中国官制命名？**
不是因为复古，而是因为这些问题唐代就想过：门下省封驳=审核者独立、科举流官=判断权流动防坐大、御史巡按不驻防=监察与被察者隔离、避籍制度=案卷不出区。一千多年的制度试错浓缩成了这些机制，比重新发明快。

**Q: 三省六部后来不是衰亡了吗？**
对，而且死因恰好是这个体系的防火墙：层级过重→所有事务走"斜封墨敕"绕开制度→制度名存实亡。所以本体系的红线是小任务必须走快捷通道（密揭/直答）、御史不得成为发布瓶颈、新增官职必须先答"对应什么真实缺口"。
